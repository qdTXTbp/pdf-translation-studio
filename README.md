# PDF 翻译工作台

本地运行的 PDF 学术翻译工具。引擎用 **BabelDOC 0.6.4**（保持版面的双语/单语 PDF 翻译），
翻译走 **DeepSeek API**。全部在本机跑，只把文本发给模型，文件不出本地。

## 快速开始

```
1) 解压到任意目录（路径里别放特殊字符）
2) 双击  start.cmd
3) 首次运行会自动装好引擎（约 500 MB，需联网一次），然后浏览器自动打开
4) 在「设置」页填入 DeepSeek API Key
5) 拖入 PDF，点开始
```

**不需要预先安装 Python 或任何依赖**——解释器和引擎都在 `runtime\` 里，
第一次运行时自动补齐。装完以后每次启动都是秒开。

首次安装中途关掉或断网都不要紧，重新双击 `start.cmd` 会接着装，已下载的部分不白费。

**环境要求**：Windows 10/11 64 位。首次安装需联网（约 500 MB），
之后翻译时首次会再下约 330 MB 的版面与字体资源（走 hf-mirror.com 镜像），
这些只在第一次发生。

## 启动

```
双击  start.cmd
```

浏览器会自动打开 `http://127.0.0.1:8760`。端口被占用时设环境变量 `PDFSTUDIO_PORT` 换端口。

要是已经在运行，再双击一次只会把浏览器打开，不会起第二个实例。

首次使用先去 **设置** 页填 DeepSeek API Key（存在本机 `config.json`，不外发）。

## 产出说明

每次翻译生成两份：

- `xxx.no_watermark.zh.mono.pdf` — **纯中文单栏**，版面宽度与原文一致。日常阅读用这份。
- `xxx.no_watermark.zh.dual.pdf` — 左原文、右译文并排，宽度是原文两倍。

产出按钮：**用 Edge 打开**（直接调 Edge，不依赖浏览器内嵌 PDF）、**下载**、**定位**（在资源管理器里高亮）。

## 图像型 PDF（扫描图 + 文字层）

有些出版商排版是「整页扫描图 + 一层不可见文字」。这种 PDF 直接翻译会出现两种坏结果：
引擎把译文画在底图**下面**（看不见），或者剥掉底图（**图表、公式、版面全丢**）。

本工具用引擎的 `--ocr-workaround`：**不动任何原有内容**，只给译文铺一层不透明底衬，
把底下的原文盖住。结果就是原图和版面一字不动、译文盖在上面清晰可读。

工具会自动识别这类 PDF 并启用；也可以在翻译页手动勾「强制底衬模式」。
普通电子版 PDF 不受影响。

## 译文字号与自动填充

引擎按原文块自动推算译文字号，密集日文论文上会偏小，且**守着原文位置不做填充**，
中文比日文紧凑，段落之间就会留下成片空白。BabelDOC 没有对应的命令行参数，
所以这两件事都在产出后直接改写内容流。

**译文字号×** 滑块范围 0.8–1.6，默认 1.0，作用在整份译文的统一缩放。

**自动填充空白**（默认开）是逐段自适应的，比统一缩放精确：内容流里每个字形都是一个
独立的 `BT ... Tf x y TD` 块，坐标是绝对页面坐标，所以段落边界可以由字形坐标聚类还原
（同一 y 成行，行距连续且左边界一致成段）。每段再按它**实际可用的空间**放大字号、
按同比例拉开行距：

- **这个 pass 只放大，从不缩小。** 密集排版的期刊里段落净空常常比字还小（实测行距
  4.5pt 对 6pt 字形），任何"这段放不下"的判定都会在正文上误报，缩小它等于破坏引擎
  已经排好的版面。译文字号偏小是引擎自己的取舍，不该由这一步推翻。
- 放大上限 **×1.08**，非常克制。放大是唯一会遮挡图的动作，而遮挡的视觉损失远大于
  它填回来的空白。
- 纵向余量按基线的真实分布算：字形墨迹约 **0.78 em 在基线上方、0.22 em 在下方**，
  所以约束是「本段末行的下缘」对「下一段首行的上缘」。按整个 em 框估会高估需求好几倍。
- 横向余量 = 到该栏右边缘的距离，**只允许超出 2pt**。右边界取页面上的**真实图形障碍**
  （矢量绘图 + 位图，面积超过页面 55% 的整页底图除外）与该栏边界的较小值——
  段落右侧真有图时收紧到图的左缘，纯空白处则放开到栏边界。这比只看"最宽文字行"
  可靠：一个窄段落旁边的图，它的可用宽度一直到图为止。
- 系数取各约束的较小值；`k <= 1.005` 的段落直接跳过。

**它能减少空白，但填不满页面，这是设计如此。** 这一步只改字号和行距，**不移动段落位置**，
所以只能吃掉段落自身周围的余量。实测垂直覆盖从 81.0% 提升到 81.2%——**很有限**。
页面下方那种成片空白（图下方、末段到页脚之间）要填，必须把段落整体挪过去，
而"哪里是真空白、哪里是图表区"没有可靠判据，挪错的代价是正文压掉图，
比留白严重得多。所以宁可保守。

**字号和字符间距必须同步缩放。** 内容流里每个字形都用各自的 `TD x y` 定位，
字体变大只会让字形变宽、不会自动推开后面的字，所以只改 `Tf` 会让相邻字符叠在一起。
放大的 x 偏移是以**段落左边缘**为基准等比拉开的：

```
new_x = x_left + (x - x_left) * k
new_y = y_top  - leading * k * line_index
```

**这一步是幂等的。** 处理后会在 PDF metadata 的 keywords 里留下
`auto-filled-by-pdfstudio` 标记，再次运行直接跳过——否则缩放系数会层层累乘，
把文字压到 3pt 去。

dual 页的译文层藏在两层 Form 里（页面流调用 `fzFrm0`/`fzFrm1`，两者又各自只调用一句
`/fullpage Do`），而且 `fzFrm1` 的矩阵把内容右移了半页宽，所以字号坐标是**半页局部坐标**。
填充会走进去定位真正带文字的子树，并且**只动右半的译文层，左半原文保持逐字节不变**。

## 逐段对照阅读视图

翻译完成后会在 dual PDF 旁边生成一份 `*.zh.dual.对照.html`，在工作台里点
**对照阅读** 直接打开。它做的是浏览器扩展那类工具的核心体验：**原文和译文逐段并排**，
而不是把译文硬塞回原版面。

这样做的价值不在于好看，而在于**它绕开了单语 PDF 绕不开的三个约束**：

- 不需要把译文塞进原位置，所以不存在遮挡、越界、字号被压缩的问题。
- 原文永远在旁边，**漏译一眼就能看到**，而不是变成屏幕上突兀的一段外文。
- 段落不必强行等长，中文比原文短多少都不影响阅读。

数据来自 dual PDF——它是唯一一份**原文和译文描述同一页同一高度**的产物，
左右两半天然对应。实现上不是简单对半切：

- 期刊正文多是双栏，**必须先识别栏**（按左边缘聚类，间隔超过 18pt 分栏），
  再按"先左栏到底、再右栏"的阅读顺序排列。直接按 y 排序会把两栏交错在一起，
  把不相关的段落粘成一段（实测第 1 页段落数会从 18 掉到 6）。
- 栏切换处**强制分段**，因为两栏的 y 范围可能重叠。
- 段落边界取"间距 > 众数行距 × 1.9"，用众数而不是相邻行距，避免单个松散行把段落切碎。
- 左右配对**按纵向重叠比例**（重叠量 ÷ 较短段高度），阈值 0.34。不能只看绝对重叠量：
  段落都很高，同页任意两段都会重叠一点，那样每个原文段都能"找到"译文，真实的漏译就被掩盖了。
- 配不上译文的原文段标成 **未译出**（黄色底），顶部统计里给出总数，可一键过滤。

页面还带搜索（原文译文一起搜）、只看未译出、深色模式，都记在 localStorage。

## 多语言混合的文档

`--lang-in` 在这条代码路径里**是未使用参数**（`converter.py` 里明确标着
"保留参数但添加未使用标记"），prompt 里也只提目标语言。所以**引擎不依赖源语言，
模型看到什么就译什么**，法语、葡萄牙语混英语的论文可以正常处理，
不必为每种语言单独跑一遍。实测一篇葡萄牙语论文（`Mulitização em refratários`）
开 `auto` 就正常译出。

真正的短板在**术语表**：内置的 25 张表都是"某语言 → 中文"，英语术语能命中，
法语同义术语不会。混排文档里同一个概念在英语段和法语段会各译各的。
需要一致性时，把该语言的术语补进 CSV（`source,target,tgt_lng` 三列，
`tgt_lng` 填源语言代码）即可，机制上已经支持多语言并存。

## 与浏览器扩展产出的差距（实测）

拿同一篇论文（葡语，双栏，8 页）逐项对比过同类工具的 dual 产出，两者
**用的是同一个引擎**——页面尺寸、左半原文行数、字体集合完全一致，差异只在参数。

结论按项列出，都是量出来的：

| 指标 | 本工具 | 参考产出 |
|---|---|---|
| 译文正确性 | 莫来石化 / 耐火浇注料 ✓ | 多晶化 / 多路复用反应 / 耐火混凝土 ✗ |
| 右半文字重叠对 | 127 | 129（相当） |
| 越界行（超出页边） | **1** | 0 |
| 字号取值数 | **27** | 21 |
| 行数 | 554 | 568 |

**译文质量上本工具更准**：参考产出把 `mullitization` 译成"多晶化"、
把 `in-situ` 那句译成"原位多路复用反应"，术语表没有拦住。这几处是硬错误，
不是风格差异。

**观感上的差距来自两点，都已处理**：

- **放大档位量化到 0.05**。每段各自算余量，连续系数会让每段字号都不同
  （全文 45 种），量化后降到 26 种，接近参考产出的 21 种。
- **溢出段落收窄**。引擎重建段落后可能让长行超出栏边，收窄 10% 以内即可收回：
  越界从 8 行降到 3 行。

### 底衬模式是个陷阱：不要默认开

`--ocr-workaround`（底衬）看起来很诱人——它给译文垫实底，引擎因此能把文字
缩进栏内，**越界从 8 行降到 1 行**。我一度把它设成默认开启。

**它同时抹掉图里的所有文字。** 引擎给**每一个**文字对象都垫实底，包括图内的
坐标轴刻度和标签。对一篇含相图的论文做像素采样：

| Y 轴刻度 | 源 PDF 墨迹 | 底衬开启 | 底衬关闭 |
|---|---|---|---|
| 2100 | 0.119 | **0.000** | 0.117 |
| 2000 | 0.134 | **0.000** | 0.132 |
| 其余 14 个 | ~0.11 | **全部 0.000** | 全部正常 |

**16 个刻度、连同 X 轴数字和轴标题，全部变成纯白。** 图内文字没有译文需要
盖住原文，它被垫底纯粹是引擎的副作用，而损失是一个图彻底废掉。

所以底衬默认**关闭**，只对图像型 PDF 自动启用（`_is_image_pdf`）——
那种 PDF 的文字层是隐形的，不开底衬根本显示不出译文，是唯一非开不可的场合。

溢出改用**收窄字号**处理，这是无损的：只动溢出的那几行，不碰任何图元。

判断"图形有没有被盖"不能只看文字层：被实底盖住的字**仍在文字层里**，
`get_text()` 照样能提取出来。必须**渲染成位图采像素**，看色块上的墨迹密度。

## 关于"漏译"

用"右半是否有汉字"扫出来的"未译内容"里，绝大多数**并不该译**：
参考文献条目、图注（`Figure 2: SEM micrographs`）、邮箱地址、坐标轴标签。
引擎自己报告的未译段落数才是真实指标，这篇是 5/86。

图注不译是引擎把它归入图元处理的结果，不是失败。对照视图里点
**只看未译出** 能直接看到真正没译的段落。

## 排版体检（layout_check.py）

排版问题靠眼睛发现太晚，所以每次产出后自动跑一遍体检，把缺陷变成日志里的数字。
单独使用：`python layout_check.py out/xxx.dual.pdf`。

体检报告的内容：

- **越界行数**与最大超出量——文字越过栏边
- **字号集中度**——主档占多少、有多少种字号、多少不在 0.5pt 网格上
- **近重复字号**——两个读者分不清的字号同时在当主档
- **同栏相邻行字号跳变**——眼睛最先抓到的不协调
- **译文行互相重叠**的对数
- **实底压住图元**的处数

实测同一篇论文：

| 指标 | 本工具 | 参考产出 |
|---|---|---|
| 越界行 | **0** | 0 |
| 字号种类 | **21** | 16 |
| 主档 | 10pt(56%) | 10pt(84%) |
| 非网格字号 | 6% | 3% |
| 重叠对 | **94** | 129 |

### 体检抓出的三个缺陷

**栏边界取自最宽行**。原实现用 `widest + 2.0` 当栏右边界，而越界的行
**按定义就是全页最宽的行**——拿它当基准，基准就和越界对齐了，缩放系数
算出来约等于 1.0，于是"没有需要修的"。三条超长行连续多轮存活就是这么来的。
改用**众数**（`round(x1)` 的众数）当正文真实右边界，越界立刻归零。

**放大没有门槛**。每段各自算余量，只要有一点空间就放大几个百分点。
代价是：5% 的放大填不满什么空白，却凭空造出一个新字号——一篇论文的
主档原本是 10pt(43%)，运行后多出 9.5pt(23%) 作为第二个主档，两个字号
读者几乎分不出，这正是"字体大小不协调"的来源。现在放大要求至少 **10%**
（`MIN_GROW`），收窄不受此限（越界必须收回，由 `min_scale` 兜底）。

**分段没有列检测**。双栏期刊的左右栏在垂直方向交错，只按 `y` 排序会让
两栏交替出现。而判断段落结束的条件之一是"某行左边界明显偏左"（段首反缩进），
**每次跨栏都会触发它**——一页 4 个段落被切成 20 段，每段只有 2 行，且
一半来自左栏、一半来自右栏。这些碎片随后各算各的缩放系数，于是**同一个
段落被渲染成两种字号、两种左边距**：

```
修复前   y=518 x0=281.7  9.0pt  ← 碎片一
         y=532 x0=281.7  9.0pt
         y=547 x0=307.6 10.0pt  ← 碎片二，缩进 26pt、字号差 1pt
         y=562 x0=307.6 10.0pt
修复后   y=517 x0=307.6 10.0pt  ← 五行同段，对齐且同字号
         ...
```

现在先按左边界把行聚成列（`GUTTER_GAP = 60`：这份文档的栏间距约 240pt，
段首缩进约 20pt，取中间值即可分开），**每列内部独立分段**，两个判断条件
只在同一列内比较。全文块→段的压缩比从"每 2 行一段"回到 150 段。

## 图内文字保护（protect_figures.py）

引擎把图里的文字当正文重排，代价是实的。在一篇含相图的论文上实测：

- Y 轴刻度 `2100`、标签 `mol% Al2O3` 丢字符（`mol% Al2O3` 变成 `p% Al2O`）
- `10 20 30 40 50 60` 粘成 `10 2030 40 50 60`
- 图区字符数 104 → 103。对照的浏览器扩展同样如此，所以这是"重建整页"这个思路的固有代价

### 为什么不是"检测图区然后整块还原"

那个思路试过，不成立。图框、栏线和绘图对象会聚成一个大框，把旁边的正文一起圈进去。
实测 8 个候选图区**全部**被"含正文"守卫否决（还原 0 处），而放宽守卫就会把译文涂掉。
**图和正文在坐标系里是交织的，按区域切不开。**

### 改用行级判定

图内文字有正文不具备的三个特征，同时满足才还原：

| 特征 | 图内标注 | 正文/标题 |
|---|---|---|
| 长度 | 短（`2100`、`10 20 30`） | 占满整栏 |
| 字号 | 小（6–10pt） | 标题 14–16pt |
| 位置 | 紧贴线条 | 不贴 |

只还原该行自己的矩形，误判的代价是一行而不是一整块。再加一条：**含汉字就跳过**——
说明那是已经被正确翻译的表头，不是图内原文。

### 效果（15 页论文）

| 指标 | 数值 |
|---|---|
| 还原行数 | 159 |
| 与原文像素一致 | **159 / 159（100%）** |
| 误保护的中文行 | 0 |
| 体积增量 | **+0.20 MB**（1.10 → 1.30 MB） |

体积控制：截图按 3× 渲染（约 216 dpi），并且**无彩色的行以灰度单通道存储**，
这一项就把增量从 +2.7 MB 压到 +0.2 MB。彩色标注仍保留 RGB。

### PaddleOCR 的位置

它是**可选依赖**，只用于报告还原了哪些文字。还原本身不需要它——
没有安装时走"无度量"分支，功能照常，不会报错。想启用就装：

```
runtime\python\python.exe -m pip install paddleocr paddlepaddle
```

## 扫描件（没有文字层的 PDF）

扫描仪出来的 PDF 只有整页位图，**一个字符都没有**。实测一份 ScanSnap 扫描件：

```
生成器: Adobe PDF Scan Library 1.0.0 / PFU ScanSnap Manager
text_layer_chars = 0
每页: 1 张全页图片，0 个矢量对象
```

翻译链路第一步就是提取文字层，没有文字层就无从下手。工具会先 **OCR 出文字层再翻译**：

```
扫描页（纯位图）
  → OCR：文字 + 每行的坐标
  → 以 render mode 3（不可见）写回文字层
  → 页面变成"全页底图 + 隐形文字层"
  → 后续流程照常接管（底衬模式保留整页图像）
```

最后那个形态正好是 `scan_text_layer()` 已经能识别的，所以术语表、版面填充、排版体检、
对照视图、图内文字保护这些能力全部可以复用，不需要改动。

### OCR 后端

可插拔，按效果从高到低自动选择：

| 后端 | 体积 | 效果 | 安装 |
|---|---|---|---|
| **PaddleOCR-VL**（0.9B VLM） | ~1.8 GB | **最好**，理解版面与公式 | `pip install paddleocr paddlepaddle-gpu` |
| **rapidocr-onnxruntime** | ~20 MB | 够用，复用引擎自带的 onnxruntime | `pip install rapidocr-onnxruntime` |

都没装时，OCR 步骤会跳过并提示安装命令，同时保留"该 PDF 没有文字层"的说明。
装哪个都能工作，`_backend()` 会自动挑可用的那个。

### 缓存与进度：OCR 是扫描件任务里最慢的一步

实测 rapidocr（onnxruntime CPU）**每页 3.9–6.4 s**，逐页串行，13 页约一分钟，
比翻译本身还长。所以做了两件事：

- **结果缓存**：文字层写在 `work/<文件名>.ocr.pdf`。**源文件没变就直接复用**，
  同一份扫描件再译一次不再重扫；只有源文件比副本新时才重新识别。
- **逐页进度**：识别期间持续上报 `OCR 识别扫描件（n/N 页）`，进度条同步推进。
  改之前这一步不产生任何事件，界面会整整一分钟停在 0%、看起来像卡死。

实测同一份 13 页扫描件：首次（含 OCR）**117 s** → 命中缓存后 **约 50 s**。
## 文字层错序的页：译文和原文叠在一起

有些出版社的 PDF 把一页的文字拆成很多短段，**内容流里的顺序不是阅读顺序**。
引擎按内容流顺序把相邻文字块并成“段落”，于是把不同行的碎片拼成一段：

```
e been know nces of zeolit tic lava flow ns were obta k-forming con s. Most zeolit
r submicrosc er, deposits o ential. among the ks, and they ironment. A s, but only eig me, chabazite
```

模型只能照着这堆碎片逐字翻，译文不成句；引擎再把中文按碎片的原坐标放回去，
中文就和残留的英文叠在同一行——**看起来既像翻译错，又像排版错，其实是同一个原因。**

页面的特征是可以用数字量的。实测一份 18 页期刊论文，三页异常、其余正常：

| | 异常页（1、5、12） | 其余页 |
|---|---|---|
| 平均词长 | 4.21–4.35 | 5.43–6.02 |
| ≤2 字符的“词”占比 | 34–35% | 18–22% |

两者之间有断层，判定阈值取在中间，并且额外要求“这一页本身不是扫描图”，
免得把扫描件又栅格化一遍。干净文档实测不误报（mullite 那篇 → 命中 0 页）。

### 开关：自动重建错序页（OCR）

默认开。命中时**只处理那几页**：

```
命中页 → 渲染成 200 dpi 位图（成为页面内容，坏掉的文字层进不了引擎）
       → 原文文字块涂白（页面已是位图，只能盖）
       → OCR 写回一层顺序正确的隐形文字层
其余页 → 原样复制
```

日志会写清楚动了哪几页：

```
[重建] 第 1、5、12 页的文字层顺序错乱，引擎会把不同行的碎片拼成一段。正在 OCR 重建这几页…
[重建] OCR 重建（rapidocr）：3 页、95 段文字层已重写
[重建] 这几页已换成位图 + 正确顺序的文字层；原文已抹白，不会再与译文叠在一起。
```

重建结果缓存在 `work/<文件名>.rebuilt.pdf`，源文件没变就不重复 OCR。

**代价**：这几页的文字变成位图（200 dpi，正常阅读和放大都够用）。

两个细节让它不至于“把原文抹没了”：

- **双语对照的左半页会自动换回你的原始文件**（左列仍显示原文），只有右半页是位图底衬。
- 涂抹只覆盖 **OCR 认出来、稍后会重画**的那部分文字块；OCR 漏掉的内容原样保留，
  不会被无谓地涂白。

### 顺带修掉的坐标 bug（扫描件同样受益）

原来的 `ocr_layer.py` 在写隐形文字层时多做了一次 `page_h - y` 翻转。
PyMuPDF 用的是**左上角原点**坐标，`insert_textbox` 写入时自己会换算，
那一次翻转把整层文字**上下镜像**了：页脚的文字跑到页顶、标题落到页脚，
引擎照着这些镜像位置排版，译文就压到图上，整页看起来错乱。

实测（18 页论文第 1 页）：

| | 标题 | 页脚 |
|---|---|---|
| 源文件 | y=63 | y=781 |
| 修复前 | y=710 | y=1.4 |
| 修复后 | y=64.5 | y=778 |

同一个函数也被扫描件 OCR 使用，所以**此前所有扫描件的文字层都是镜像的**，
这条修复对全部 OCR 路径生效。`work/` 下用旧代码生成的缓存必须删掉重建。

### 顺带修掉的一个旧行为

`scan_text_layer()` 现在要求**过半页面**是全页底图，才把文档判为扫描型。
以前只要有一页是大图就会让整篇走底衬模式，而底衬模式**保留原文**，
于是正常的文字页反而出现“中文和英文叠在一起”。上面这份 18 页论文里 15 页是正常文字页，
正是靠这条规则才不会被那 3 页拖下水。

### 段落合并：这一步决定译文能不能读

OCR 天然按**行**输出。如果每行写成独立文本对象，引擎就会**逐行翻译**，
句子被切断后译文必然是碎的。在一份 1969 年的扫描件上实测：

| 处理方式 | 结果 |
|---|---|
| 逐行写（699 行） | `*Publication authorized by the Dircctor...` → `由美国地质调查局局长授权的ation。` + `*公共` |
| **合并成段（321 段）** | `a large spread of location of the p-T univariant curve...` → `各种多型变体对之间p-T单变曲线位置的扩展` |

合并规则：左边界接近（同栏）、垂直间距小于 1.8 倍行距、字号接近。

**两个实测踩到的坑**：

- **OCR 产物不能放进 `out/`**。重试逻辑会清空 `out/*.pdf` 来丢弃半成品，
  会把刚生成的 OCR 副本一起删掉（实测报 `文件不存在：...ocr.pdf`）。现在写在 `work/`。
- **`insert_textbox` 排版失败时静默不写**。OCR 的框很紧，合并后文本变长就放不下，
  结果 410 个段落一个字符都没写进去。隐形层的字号不影响显示，所以现在会逐步降字号
  直到写入成功。

## 重试策略：哪些失败值得重跑

引擎对翻译失败的段落会**保留原文并以退出码 0 结束**，所以一次"成功"的运行
可能夹着几段没译的正文。为此本工具会检查成功率，低于 98% 才考虑重跑。

但失败有两种，混在一起会白花钱：

**网络/接口异常**（`Connection error`、`Error code: 429 / 5xx`、`Read timed out`）
——**瞬时**，重跑真的能救回来，值得重试。

**模型对同一提示词的固定回答**——**确定性**，包括：

- `Translation result is the same as input`（模型判定这段无需翻译）
- `Error Unterminated string ... during translation. try fallback`
  （模型对这一段**始终**返回非法 JSON）

提示词一样，答案就一样。参考文献条目和英文图注多半落在第一类，而且**模型的决定是对的**：
把 `Am. Ceram. Soc. Bull. 51, 7 (1972) 577-581` 译成中文会毁掉一条可检索的引用。

判定规则（`server.py`）：

1. 成功率 ≥ 98% → 结束。
2. 本轮的（成功段数, 总段数）与上一轮**完全一致** → 结束，再跑也只会得到同一个结果。
3. 本轮**没有任何瞬时异常** → 结束，剩下的都是模型的固定回答。
4. 否则重跑（最多 3 次），日志里写明还剩几段、原因是什么。

统计只覆盖**本轮新写入的日志**（`_attempt_failures(logf, start)`）。日志是**追加**写的，
早先的版本扫描整个文件，于是第二次尝试必然看见第一次的错误，永远"有瞬时异常"，
注定跑满三次。

实测同一篇 277 段的综述（`Review of mullite synthesis routes by sol–gel method`）：

| | 改前 | 改后 |
|---|---|---|
| 引擎尝试次数 | 3 | **1** |
| 译出段落 | 252/277 | 252/277（完全一致）|
| 耗时 | 31.6 + 30.9 + 31.5 ≈ **94 s** | **39 s** |

译文和产出完全一致，省下的纯粹是重复调用。

这里要更正早先的一个说法：**重跑并不便宜**。引擎缓存对这类失败无效——三次尝试
每次都实打实地重发请求、重跑版面解析，单次耗时几乎相同，所以"多跑几次"就是
实打实的三倍时间。

对照视图里这些段落会显示成"未译出"（黄色底），点**只看未译出**能确认
它们是文献条目而不是漏译的正文。

## 译文缺失与特殊字符

引擎在单段翻译失败时**静默保留原文**并仍然以 0 退出，所以缺译不会表现为报错，
看起来就是「右半还是一半日文」。判定要看日志里的成功率：

```
Translation completed. Total: 105, Successful: 101, Fallback: 4
```

跑完不能只看退出码：**引擎对翻译失败的段落会静默保留原文，仍然 exit 0**。
所以工作台按 `Successful/Total` 判定状态，**只要不是 100% 就标 `warn` 并说明还剩几段**。
是否重跑由上面的分类决定（最多 3 次）；确定性失败不再重复调用。

实测同一文件同一参数，正常是 99~101/105，异常那次掉到 14/105——而且**36 秒就跑完了**
（正常要 1–2 分钟），说明请求是被批量快速拒绝的；同时 completion token 从 5282
暴涨到 215262（模型退化后疯狂重复输出），日志满屏
`Expecting value: line 1 column 1 (char 0)`。

为压低这类故障的发生面，还做了两件事：**默认关闭自动术语提取**
（`--no-auto-extract-glossary`，它是一条额外的 LLM 调用链，失败时会连续刷
`Error during automatic terms extract`），以及上面说的自动选表。

### 漏译：一类是偶发，一类是模型拒绝

日志里有两组完全不同的告警，处理方式也不同：

- `Error ... during translation. try fallback` —— **API 侧偶发异常**。这类靠重跑能恢复，
  上面说的 14/105 就是。
- `Translation result is the same as input, fallback.` —— **模型把输入原样吐回来了**。
  这类**重跑多少次都一样**，因为它由内容决定，与网络无关。

第二类集中出现在**日文正文里夹着大量化学式**的段落上（实测某段 9 行正文整段未译，
内容形如 `Al2O3・SiO2の組成まで固溶領域は広がる。ムライト固溶体のAl2O3量が増加するとb0は…`）。
模型把它读成"技术记号，不需要翻译"。判定阈值是
**编辑距离 < 5 且输入超过 20 token** 就回退，所以照抄必被判失败。

有效的对策只有一个：**`--add-formula-placehold-hint`（默认开）**，实测把这种失败
从 8 段压到 5 段、同文回退从 21 次压到 15 次。试过但**无效或有害**的：

- `--custom-system-prompt` 写一段"公式要原样保留、但日文正文必须翻译"的提示词，
  **反而更差**（失败 5→7 段，同文回退 15→21 次）——提示词强化了模型"这类段落
  属于不可译记号"的判断。
- `--openai-model deepseek-reasoner`，**灾难性**：`Successful: 8, Fallback: 97`，
  耗时从 54 秒涨到 245 秒。它的思维链破坏了解析。
- `--disable-same-text-fallback` 只会让原文冒充译文混过判定，不解决问题。

剩下的 5 段里，参考文献条目（`文献9) の p. 188-90.`）和作者署名本来就不该翻译，
**真正的残留问题是那一段化学式密集的正文**。这是模型侧行为，客户端改不动；
要么换用别的模型，要么在产出后手工补这一段。

希腊字母（`θ`/`α`/`δ`/`γ`）偶发丢失、出现 `-及 -氧化` 这种痕迹，
成因相同——是模型输出时丢的，不是字体缺字形：同一文件重跑一次就正常出现
`θ-和α-氧化铝`。试过 `--primary-font-family serif`，无效。

**另有一类"丢失"其实是文本层映射缺失，不是视觉丢失。** 实测译文的文本层里
`°`、`±`、`μ`、`θ`、`δ`、`γ`、`·` 出现次数为 **0**，但同一份 PDF 用 OCR 能稳定
读出 `980°～1005°C`——**字形渲染出来了，只是没有 ToUnicode 映射**。后果是
屏幕上正常、**复制或搜索时符号消失**。这是引擎的字形子集化行为，改字体族无法解决，
需要在产出后重建 CMap 才能根治。

真正会丢的是小数：`\d+\.\d+` 从原文 89 处掉到译文 9 处。这一项尚无对策。

## 术语库

覆盖 **25 个学科、1577 条**，放在 `glossary/`，每学科一个 CSV：

| 领域 | 领域 | 领域 | 领域 | 领域 |
|---|---|---|---|---|
| 通用学术 | 数学 | 统计 | 物理 | 化学 |
| 材料 | 生物 | 医学 | 神经科学 | 计算机/AI |
| 电子/通信 | 机械 | 土木 | 能源 | 环境 |
| 天文 | 地球科学 | 经济 | 管理 | 心理学 |
| 语言学 | 哲学 | 法学 | 教育 | 农业 |

翻译页有「启用的术语表」勾选区。**默认开启「自动选择相关术语表」**：翻译前会先扫描
文档前几页正文，按每个表的术语在文中出现的多少打分，只加载最相关的最多 3 个表。
这份 9 页日文论文实测只选出 `materials-zh`（命中 5 个术语）和 `physics-zh`（命中 1 个），
**25 个表压到 2 个**。取消勾选就回到手动模式，由你在下面自己勾。

这样做的意义不只是省 token：表选得少，注入 prompt 的术语就少，一个无关领域的短词
恰好藏在普通词里（`sol` 在 `solid`、`aging` 在 `imaging`）而被强行套用的机会也小得多。

格式三列：

```
source,target,tgt_lng
metal alkoxide,金属醇盐,zh
```

### 术语是怎么生效的（重要）

引擎**不做字符串替换**。它按批次扫描正文，把命中的术语组成 markdown 表格注入 LLM prompt：

```
## Glossary
- Always use the exact target term.
- If glossary does NOT include a term, translate it naturally.

## Glossary Tables
### Glossary: materials-zh
| Source Term | Target Term |
|-------------|-------------|
| metal alkoxide | 金属醇盐 |
```

三个推论：

**只有真正出现在该批次文本里的术语才会被注入**——所以全选 25 个表不会把 1577 条全塞进 prompt，无关领域的表几乎不产生成本。

**子串包含无害**。`particle size` 是 `particle size distribution` 的子串，但两者都会进表，LLM 自己选对的。这类「自冲突」在全表里有 95 处，不需要处理。

**真正要防的是「短词藏在无关词里」**：正文出现 `solid` → `sol` 命中 → prompt 里带着 "Always use the exact target term" 出现 `sol | 溶胶`，属于主动误导。所以库里**不放孤立短词**：`corona`（藏在 coronary/coronavirus）、`genetics`（藏在 epigenetics）已删，改成把更长的兄弟词补进表（`impurity`、`epigenetics`、`metagenomics`、`photonic crystal`）。新增条目时请守住同一条线：**要么是多词短语，要么长到不可能成为别的词的子串**。

### 成本

全选 25 表时，那篇 9 页日文论文的 prompt 从 14797 涨到 20096 token（约 +36%）。只勾相关领域（例如材料 + 化学 + 物理 + 通用学术）可以把这个增量压回去。

### 编辑

**术语库**页可直接增删改存任一 CSV，也可新建。保存时自动过滤空行、把逗号与换行替换为空格。

  protect_figures.py   图内文字还原（产出后处理，需 PyMuPDF；PaddleOCR 可选）
  ocr_layer.py         扫描件 OCR 补文字层（需 rapidocr 或 PaddleOCR-VL）
  config.example.json  配置模板

引擎的模型与字体资源（约 330 MB）由 BabelDOC 自己放在
`%USERPROFILE%\.cache\babeldoc`，不在项目目录里，首次翻译时自动下载。

### 为什么内置解释器

打包时把 Python 一起放进去，是为了让"解压即用"成立——否则得先装 Python、
再装引擎，用户要跨好几道坎。代价是压缩包 22 MB（大多是 Python 运行时）。

引擎本身（含 cv2/scipy/onnxruntime 等依赖，约 660 MB）没有塞进包里，
因为那会让压缩包超过 GitHub 100 MB 的单文件限制。所以首次运行需要联网装一次，
`start.cmd` 会自动完成，用户不需要做任何额外操作。

**一个坑**：uv 提供的便携 Python 带 PEP 668 的 `EXTERNALLY-MANAGED` 标记，
pip 默认拒绝往里装东西。打包前已删掉 `runtime\python\Lib\EXTERNALLY-MANAGED`，
脚本里也带了 `--break-system-packages` 双保险。

## 排查

| 现象 | 处理 |
|---|---|
| 双击 start.cmd 一闪而过 | 从命令行运行 `cmd /k start.cmd` 看报错；常见是包没解压完整 |
| 首次安装报网络错误 | 重新双击即可续装；引擎走 pypi 阿里云镜像，模型走 hf-mirror |
| 页面打不开 | `logs\srv.err`；端口被占用试 `set PDFSTUDIO_PORT=8761` |
| 产出没有中文 | 看 `logs\<job>.log` 是否有 `Error code: 401`，多半是 Key 无效 |
| 译文看不见 | 勾「强制底衬模式」重跑 |
| 图形里的字不见了 | 别开底衬模式，它会盖住图内所有文字 |
| 术语没生效 | 日志里找 `Loaded glossary 'xxx' with N entries` 确认已加载 |
| 只要部分页 | 填页码范围，省 token |

### 关于 .cmd 文件的编码

Windows 的 `cmd.exe` 需要 **CRLF 换行**，且按系统代码页（简中是 GBK/936）
读取批处理文件。用 LF 换行或 UTF-8 编码保存的 `.cmd` 会被解析成碎片，
报出 `'ing?' 不是内部或外部命令` 之类的错，或者中文全部乱码。

本项目的 `start.cmd` 保存为 **CRLF + GBK**。改动它时请保持这个编码，
否则会重现上述故障。

`prompt_tokens=0` 但状态是 done 是**正常**的——命中了本地缓存，没重复计费。
判定真实结果的依据是日志里的 `Translation completed. Total: N, Successful: M`。
